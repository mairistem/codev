## Purpose

`compagnon doctor` tells a team what its compagnon setup still lacks — configuration,
skills, specs, decisions, inherited sources, repository integration,
validation — and the exact command or skill that fixes each gap, without
modifying anything.

## ADDED Requirements

### Requirement: `compagnon doctor` runs a fixed list of read-only checks

`compagnon doctor` SHALL evaluate the following checks, reported in this order, each
with a stable `id`, and report each one as `ok`, `missing` or `warning`,
with a stable `code` (`ok` when the check passes), a one-line message and,
when not `ok`, a one-line fix naming the exact command or skill:

| id | passes when | otherwise | code | fix |
|---|---|---|---|---|
| `config.rules` | `rules:` has at least one entry, inherited ones included | missing | `rules_missing` | `/compagnon-configure` |
| `config.language` | `language:` is set in `_compagnon/config.yaml` | missing | `language_missing` | add `language: <code>` to `_compagnon/config.yaml` |
| `skills` | every configured workflow has its skill, generated by the running compagnon version | missing | `skills_missing` or `skills_outdated` | `compagnon update` |
| `sources` | every inherited git source is pinned in `_compagnon/compagnon.lock` and present in the cache, and the lock pins no undeclared source | missing (unpinned or not cached) or warning (undeclared pin) | `source_unpinned` or `lock_stale` | `compagnon sources update` |
| `specs` | at least one main spec exists | missing | `no_main_spec` | `/compagnon-propose`, noting that documenting existing behavior is planned work |
| `decisions` | at least one decision is `accepted`, local or inherited | warning | `no_accepted_decision` | `compagnon decision new "<title>"` |
| `validate` | `compagnon validate` reports no error and no warning | missing (errors) or warning (warnings only) | `validate_errors` or `validate_warnings` | `compagnon validate` |
| `claude_md` | `CLAUDE.md` holds the compagnon managed section | missing | `claude_md_section_missing` | `compagnon init` |
| `ci` | a file of `.github/workflows/` or `.gitlab-ci.yml` runs `compagnon validate` | missing | `ci_validate_missing` | `compagnon init` on GitHub, otherwise add `compagnon validate --strict` to the pipeline |
| `pr_template` | the pull request template holds the compagnon managed section — GitHub repositories only | missing | `pr_template_section_missing` | `compagnon init` |

The `pr_template` check MUST be absent from the report when the repository
is not a GitHub repository. A project without any inherited source passes
`sources`. A CI line is recognized when it names `compagnon` and then
`validate`, so `cargo run --bin compagnon -- validate` counts.

`compagnon doctor` MUST NOT write any file, spawn `git`, or access the network.
Outside a compagnon project, it fails with the code `no_compagnon_root`.

#### Scenario: A freshly initialized project

- **GIVEN** a project just initialized with `compagnon init --yes` outside
  GitHub, without rules, specs or decisions
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.rules` and `specs` are `missing`, `decisions` is a
  `warning`, `ci` is `missing`
- **AND** `config.language`, `skills`, `sources`, `claude_md` and
  `validate` are `ok`
- **AND** no `pr_template` check is reported

#### Scenario: Outdated skills

- **GIVEN** a project whose skills were generated by an earlier compagnon
  version
- **WHEN** the user runs `compagnon doctor`
- **THEN** `skills` is `missing` with the code `skills_outdated` and the fix
  `compagnon update`

#### Scenario: An unpinned git source

- **GIVEN** a project declaring a git source absent from
  `_compagnon/compagnon.lock`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `sources` is `missing` with the code `source_unpinned` and the
  fix `compagnon sources update`

#### Scenario: CI recognized through `cargo run`

- **GIVEN** a GitHub project whose `.github/workflows/ci.yml` runs
  `cargo run --bin compagnon -- validate --strict`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `ci` is `ok`

#### Scenario: Doctor writes nothing

- **GIVEN** any compagnon project
- **WHEN** the user runs `compagnon doctor`
- **THEN** no file of the project is created or modified

#### Scenario: Outside a compagnon project

- **GIVEN** a folder with no `_compagnon/` above it
- **WHEN** the user runs `compagnon doctor`
- **THEN** the command fails with the code `no_compagnon_root`

### Requirement: Human output groups the checks and counts what is left to fix

The human output of `compagnon doctor` SHALL group the checks under
"Configuration", "Planning" and "Repository", one line per check with `✓`
for `ok`, `✗` for `missing` and `!` for `warning`, followed, when not
`ok`, by its fix. The last line MUST read `N check(s), M to fix`, where N
counts the reported checks and M the `missing` ones, followed by
`, K warning(s)` when K warnings are reported.

#### Scenario: Summary line

- **GIVEN** a project where 9 checks are reported, 2 `missing` and 1
  `warning`
- **WHEN** the user runs `compagnon doctor`
- **THEN** the last line reads `9 check(s), 2 to fix, 1 warning(s)`
- **AND** each `✗` line is followed by its fix

### Requirement: The exit code fails only on `--strict` with something missing

`compagnon doctor` SHALL exit with code 0 whatever it finds, unless `--strict`
is passed and at least one check is `missing`, in which case it exits with
code 1. Warnings never change the exit code.

#### Scenario: Strict with a missing check

- **GIVEN** a project where `specs` is `missing`
- **WHEN** the user runs `compagnon doctor --strict`
- **THEN** the exit code is 1

#### Scenario: Strict with warnings only

- **GIVEN** a project where every check is `ok` except `decisions`, a
  `warning`
- **WHEN** the user runs `compagnon doctor --strict`
- **THEN** the exit code is 0

### Requirement: `compagnon doctor --json` follows the JSON contract v1

`compagnon doctor --json` SHALL print exactly one JSON document with `root`,
`checks` — each with `id`, `group` (`configuration`, `planning`,
`repository`), `status` (`ok`, `missing`, `warning`), `code`, `message`
and `fix` (`null` when `ok`) — `summary` with `total`, `missing` and
`warnings`, and the `status` array of every v1 document. On failure, the
document keeps that shape with empty fields and carries the error in
`status`.

#### Scenario: JSON report

- **WHEN** the user runs `compagnon doctor --json` in a compagnon project
- **THEN** stdout is one JSON document whose `checks` entries carry `id`,
  `group`, `status`, `code`, `message` and `fix`
- **AND** `summary.missing` equals the number of checks whose `status` is
  `missing`

#### Scenario: JSON failure keeps the shape

- **GIVEN** a folder outside any compagnon project
- **WHEN** the user runs `compagnon doctor --json`
- **THEN** stdout is one JSON document with `checks: []` and a `status`
  entry whose code is `no_compagnon_root`

### Requirement: `compagnon status` hints at `compagnon doctor`

When at least one doctor check is `missing`, the human output of
`compagnon status` SHALL end with one line on stderr suggesting
`compagnon doctor`, including when `compagnon status` fails because no change is
active. The JSON output of `compagnon status` MUST NOT change.

#### Scenario: Hint on a project with missing checks

- **GIVEN** a project with an active change and no main spec
- **WHEN** the user runs `compagnon status`
- **THEN** stderr ends with a line naming `compagnon doctor`

#### Scenario: No hint when everything is in place

- **GIVEN** a project where no doctor check is `missing`
- **WHEN** the user runs `compagnon status --change <name>`
- **THEN** no line names `compagnon doctor`
