# Doctor Specification

## Purpose

`compagnon doctor` tells a team what its Compagnon setup still lacks — configuration,
skills, specs, decisions, inherited sources, repository integration,
validation — and the exact command or skill that fixes each gap, without
modifying anything.

## Requirements

### Requirement: `compagnon doctor` runs a fixed list of read-only checks

`compagnon doctor` SHALL evaluate the following checks, reported in this order, each
with a stable `id`, and report each one as `ok`, `missing` or `warning`,
with a stable `code` (`ok` when the check passes), a one-line message and,
when not `ok`, a one-line fix naming the exact command or skill:

| id | passes when | otherwise | code | fix |
|---|---|---|---|---|
| `config.rules` | `rules:` has at least one entry, inherited ones included | missing | `rules_missing` | `/compagnon-configure` |
| `config.language` | `language:` is set in `_compagnon/config.yaml` | missing | `language_missing` | add `language: <code>` to `_compagnon/config.yaml` |
| `config.keys` | `_compagnon/config.yaml` holds no key the running Compagnon ignores (top level, `mcp`, `review` or a role's mapping under `roles:`) | warning | `unknown_config_key` | `compagnon self-update` when the running Compagnon does not satisfy `compagnon_version`, otherwise correct or remove the key, naming the keys |
| `config.roles` | every role setting is valid; informational, its message lists the active roles and the disabled ones | warning | `roles_invalid` | `compagnon validate` |
| `skills` | every configured workflow has its skill, generated by the running compagnon version, and the `propose` and `apply` skills are rendered for the project's review mode | missing | `skills_missing`, `skills_outdated` or `skills_review_mode` | `compagnon update` (`compagnon update --force` for a skill it preserves as edited by hand) |
| `sources` | every inherited git source is pinned in `_compagnon/compagnon.lock` and present in the cache, and the lock pins no undeclared source | missing (unpinned or not cached) or warning (undeclared pin) | `source_unpinned` or `lock_stale` | `compagnon sources update` |
| `compagnon_version` | the running Compagnon satisfies the project's `compagnon_version`, when set, and the cached update check knows no newer release | missing (requirement not satisfied) or warning (newer release known) | `compagnon_version_unsatisfied` or `update_available` | `compagnon self-update`, or `compagnon self-update --version <X.Y.Z>` when the running Compagnon is above the requirement |
| `specs` | at least one main spec exists | missing | `no_main_spec` | `/compagnon-propose`, noting that documenting existing behavior is planned work |
| `decisions` | at least one decision is `accepted`, local or inherited | warning | `no_accepted_decision` | `compagnon decision new "<title>"` |
| `validate` | `compagnon validate` reports no error and no warning | missing (errors) or warning (warnings only) | `validate_errors` or `validate_warnings` | `compagnon validate` |
| `claude_md` | `CLAUDE.md` holds the Compagnon managed section | missing | `claude_md_section_missing` | `compagnon init` |
| `ci` | a file of `.github/workflows/` or `.gitlab-ci.yml` runs `compagnon validate` | missing | `ci_validate_missing` | `compagnon init` on GitHub, otherwise add `compagnon validate --strict` to the pipeline |
| `pr_template` | the pull request template holds the Compagnon managed section — GitHub repositories only | missing | `pr_template_section_missing` | `compagnon init` |
| `changelog` | `CHANGELOG.md` exists and its managed `[Unreleased]` section matches what `compagnon changelog` would generate now | warning | `changelog_missing` (no file) or `changelog_outdated` | `compagnon changelog --write` |

The `pr_template` check MUST be absent from the report when the repository
is not a GitHub repository. A project without any inherited source passes
`sources`. A CI line is recognized when it names `compagnon` and then
`validate`, so `cargo run --bin compagnon -- validate` counts.

When the running Compagnon does not satisfy `compagnon_version` because it is
above the requirement's upper bound, the fix MUST be
`compagnon self-update --version <X.Y.Z>`, a plain `compagnon self-update` refusing
to downgrade. `X.Y.Z` is, in this order of preference: the latest release
known to the update cache, when it satisfies the requirement; the highest
version the requirement admits, when an upper bound names it exactly (`<=`
or `=` with a full version); the lowest version the requirement admits,
when it has a lower bound. When none applies, the fix names the
requirement and asks for a release that satisfies it. When the running
Compagnon is below the requirement, the fix stays `compagnon self-update`.

The `compagnon_version` check reads the per-user update cache that
`compagnon status` maintains and never refreshes it: with no cache, or with
`CI` set or `COMPAGNON_NO_UPDATE_CHECK=1`, it only evaluates the requirement.

`compagnon doctor` MUST NOT write any file or access the network. The only
process it MAY spawn is `git`, for the local, read-only queries the
`changelog` check needs; outside a git repository, that check compares
with every archived change. Outside a Compagnon project, it fails with the code
`no_compagnon_root`.

#### Scenario: A freshly initialized project

- **GIVEN** a project just initialized with `compagnon init --yes` outside
  GitHub, without rules, specs or decisions, and no newer Compagnon release
  known
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.rules` and `specs` are `missing`, `decisions` is a
  `warning`, `ci` is `missing`
- **AND** `config.keys`, `config.roles`, `config.language`, `skills`, `sources`,
  `compagnon_version`, `claude_md` and `validate` are `ok`
- **AND** `changelog` is a `warning` with the code `changelog_missing`
- **AND** no `pr_template` check is reported

#### Scenario: Outdated skills

- **GIVEN** a project whose skills were generated by an earlier Compagnon
  version
- **WHEN** the user runs `compagnon doctor`
- **THEN** `skills` is `missing` with the code `skills_outdated` and the fix
  `compagnon update`

#### Scenario: An unpinned git source

- **GIVEN** a project declaring a git source absent from
  `_compagnon/compagnon.lock`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `sources` is `missing` with the code `source_unpinned` and the
  fix `compagnon sources update`

#### Scenario: CI recognized through `cargo run`

- **GIVEN** a GitHub project whose `.github/workflows/ci.yml` runs
  `cargo run --bin compagnon -- validate --strict`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `ci` is `ok`

#### Scenario: Doctor writes nothing

- **GIVEN** any Compagnon project
- **WHEN** the user runs `compagnon doctor`
- **THEN** no file of the project is created or modified

#### Scenario: Outside a Compagnon project

- **GIVEN** a folder with no `_compagnon/` above it
- **WHEN** the user runs `compagnon doctor`
- **THEN** the command fails with the code `no_compagnon_root`

#### Scenario: CHANGELOG.md up to date

- **GIVEN** a project where `compagnon changelog --write` was just run
- **WHEN** the user runs `compagnon doctor`
- **THEN** `changelog` is `ok`

#### Scenario: CHANGELOG.md behind the archive

- **GIVEN** a project whose `CHANGELOG.md` managed section predates the
  latest archived change
- **WHEN** the user runs `compagnon doctor`
- **THEN** `changelog` is a `warning` with the code `changelog_outdated`
  and the fix `compagnon changelog --write`
- **AND** the exit code of `compagnon doctor --strict` is unaffected by it

#### Scenario: Running Compagnon below the project's requirement

- **GIVEN** a project with `compagnon_version: ">=0.7"` and Compagnon 0.6.0 running
- **WHEN** the user runs `compagnon doctor`
- **THEN** `compagnon_version` is `missing` with the code
  `compagnon_version_unsatisfied` and the fix `compagnon self-update`

#### Scenario: A newer release is known

- **GIVEN** a project without `compagnon_version`, and an update cache knowing
  a release newer than the running Compagnon
- **WHEN** the user runs `compagnon doctor`
- **THEN** `compagnon_version` is a `warning` with the code `update_available`
  and the fix `compagnon self-update`
- **AND** no network request is made

#### Scenario: Running Compagnon above the project's requirement

- **GIVEN** a project with `compagnon_version: ">=0.5, <0.7"`, Compagnon 0.7.1
  running, and an update cache whose latest known release is 0.6.4
- **WHEN** the user runs `compagnon doctor`
- **THEN** `compagnon_version` is `missing` with the code
  `compagnon_version_unsatisfied` and the fix
  `compagnon self-update --version 0.6.4`

#### Scenario: Running Compagnon above an exact upper bound, no usable cache

- **GIVEN** a project with `compagnon_version: "<=0.6.2"`, Compagnon 0.7.0 running,
  and no update cache
- **WHEN** the user runs `compagnon doctor`
- **THEN** `compagnon_version` is `missing` with the fix
  `compagnon self-update --version 0.6.2`

#### Scenario: Running Compagnon above a requirement with no exact bound

- **GIVEN** a project with `compagnon_version: "^0.5"`, Compagnon 0.6.0 running, and
  an update cache whose latest known release, 0.6.0, does not satisfy it
- **WHEN** the user runs `compagnon doctor`
- **THEN** `compagnon_version` is `missing` with the fix
  `compagnon self-update --version 0.5.0`

#### Scenario: An unknown configuration key

- **GIVEN** a project whose `_compagnon/config.yaml` holds the top-level key
  `review_policy`, unknown to the running Compagnon, which satisfies
  `compagnon_version`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.keys` is a `warning` with the code `unknown_config_key`
  whose message names `review_policy`
- **AND** its fix tells to correct or remove the key
- **AND** the exit code of `compagnon doctor --strict` is unaffected by it

#### Scenario: An unknown key with an unsatisfied requirement

- **GIVEN** a project whose `_compagnon/config.yaml` holds an unknown key and
  `compagnon_version: ">=9"`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.keys` is a `warning` with the fix `compagnon self-update`

#### Scenario: The roles in effect

- **GIVEN** a project whose configuration holds `roles: { newcomer: never }`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.roles` is `ok` and its message lists the active roles
  and names `newcomer` as disabled

#### Scenario: An invalid role setting

- **GIVEN** a project whose configuration holds `roles: { reviewer: never }`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.roles` is a `warning` with the code `roles_invalid`
  and the fix `compagnon validate`
- **AND** `validate` is `missing`

#### Scenario: An unknown key in a role's mapping

- **GIVEN** a project whose configuration holds
  `roles: { skeptic: { cadence: weekly } }`
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.keys` is a `warning` with the code `unknown_config_key`
  naming `roles.skeptic.cadence`
- **AND** `config.roles` is `ok`

### Requirement: Human output groups the checks and counts what is left to fix

The human output of `compagnon doctor` SHALL group the checks under
"Configuration", "Planning" and "Repository", one line per check with `✓`
for `ok`, `✗` for `missing` and `!` for `warning`, followed, when not
`ok`, by its fix. The last line MUST read `N check(s), M to fix`, where N
counts the reported checks and M the `missing` ones, followed by
`, K warning(s)` when K warnings are reported.

#### Scenario: Summary line

- **GIVEN** a project where 9 checks are reported, 2 `missing` and 1
  `warning`
- **WHEN** the user runs `compagnon doctor`
- **THEN** the last line reads `9 check(s), 2 to fix, 1 warning(s)`
- **AND** each `✗` line is followed by its fix

### Requirement: The exit code fails only on `--strict` with something missing

`compagnon doctor` SHALL exit with code 0 whatever it finds, unless `--strict`
is passed and at least one check is `missing`, in which case it exits with
code 1. Warnings never change the exit code.

#### Scenario: Strict with a missing check

- **GIVEN** a project where `specs` is `missing`
- **WHEN** the user runs `compagnon doctor --strict`
- **THEN** the exit code is 1

#### Scenario: Strict with warnings only

- **GIVEN** a project where every check is `ok` except `decisions`, a
  `warning`
- **WHEN** the user runs `compagnon doctor --strict`
- **THEN** the exit code is 0

### Requirement: `compagnon doctor --json` follows the JSON contract v1

`compagnon doctor --json` SHALL print exactly one JSON document with `root`,
`checks` — each with `id`, `group` (`configuration`, `planning`,
`repository`), `status` (`ok`, `missing`, `warning`), `code`, `message`
and `fix` (`null` when `ok`) — `summary` with `total`, `missing` and
`warnings`, and the `status` array of every v1 document. On failure, the
document keeps that shape with empty fields and carries the error in
`status`.

#### Scenario: JSON report

- **WHEN** the user runs `compagnon doctor --json` in a Compagnon project
- **THEN** stdout is one JSON document whose `checks` entries carry `id`,
  `group`, `status`, `code`, `message` and `fix`
- **AND** `summary.missing` equals the number of checks whose `status` is
  `missing`

#### Scenario: JSON failure keeps the shape

- **GIVEN** a folder outside any Compagnon project
- **WHEN** the user runs `compagnon doctor --json`
- **THEN** stdout is one JSON document with `checks: []` and a `status`
  entry whose code is `no_compagnon_root`

### Requirement: `compagnon status` hints at `compagnon doctor`

When at least one doctor check is `missing`, the human output of
`compagnon status` SHALL end with one line on stderr suggesting
`compagnon doctor`, including when `compagnon status` fails because no change is
active. The hint MUST NOT appear in the JSON output of `compagnon status`.

#### Scenario: Hint on a project with missing checks

- **GIVEN** a project with an active change and no main spec
- **WHEN** the user runs `compagnon status`
- **THEN** stderr ends with a line naming `compagnon doctor`

#### Scenario: No hint when everything is in place

- **GIVEN** a project where no doctor check is `missing`
- **WHEN** the user runs `compagnon status --change <name>`
- **THEN** no line names `compagnon doctor`

#### Scenario: The hint stays out of the JSON

- **GIVEN** a project with an active change and no main spec
- **WHEN** the user runs `compagnon status --change <name> --json`
- **THEN** stdout is one JSON document and no line names `compagnon doctor`

### Requirement: `config.roles` names the roles active by domain

The message of the `config.roles` check SHALL list, besides the active and
the disabled roles, the roles whose activation is `on_domain` — with the
default settings, the six experts — each with the domain or domains that
activate it, under `on domain`. A project setting that turns an expert to
`always` or `never` moves it to the active or the disabled list.

#### Scenario: The experts in the doctor report

- **GIVEN** a project with no `roles:` key
- **WHEN** the user runs `compagnon doctor`
- **THEN** `config.roles` is `ok` and its message names `security`
  (`security`) and `privacy` (`personal-data`) under `on domain`

#### Scenario: An expert forced by the project

- **GIVEN** a project whose configuration holds
  `roles: { security: always, ops: never }`
- **WHEN** the user runs `compagnon doctor`
- **THEN** the message of `config.roles` lists `security` among the active
  roles and `ops` among the disabled ones

### Requirement: The `skills` check compares the skills with the review mode

When every configured skill is present and generated by the running
Compagnon, the `skills` check of `compagnon doctor` SHALL be `missing` with the
code `skills_review_mode` if the `propose` or `apply` skill was rendered
for another review mode than the project's: it lists the sub-agent tool
while the mode is `inline`, or does not while it is `isolated`. The
message SHALL name the skills and the project's mode, and the fix SHALL
be `compagnon update`, adding `compagnon update --force` for a skill that
`compagnon update` preserves as edited by hand. A missing or outdated skill
keeps its own code, which takes precedence.

#### Scenario: Skills rendered before switching to isolated

- **GIVEN** a project whose skills were generated in inline mode by the
  running Compagnon, then `review: { mode: isolated }` in its configuration
- **WHEN** the user runs `compagnon doctor --json`
- **THEN** the `skills` check is `missing` with the code
  `skills_review_mode`, naming `compagnon-propose`, `compagnon-apply` and
  `isolated`, and the fix `compagnon update`

#### Scenario: A skill of the other mode edited by hand

- **GIVEN** a project in isolated mode whose `compagnon-apply` skill was
  generated in inline mode by the running Compagnon, then edited by hand
- **WHEN** the user runs `compagnon doctor --json`
- **THEN** the `skills` check's code is `skills_review_mode` and its fix
  names `compagnon update --force`

#### Scenario: Skills in step with the mode

- **GIVEN** a project in isolated mode where `compagnon update` just ran
- **WHEN** the user runs `compagnon doctor --json`
- **THEN** the `skills` check is `ok`

#### Scenario: An outdated skill takes precedence

- **GIVEN** a project in isolated mode whose `compagnon-propose` skill was
  generated by an earlier Compagnon in inline mode
- **WHEN** the user runs `compagnon doctor --json`
- **THEN** the `skills` check's code is `skills_outdated`
