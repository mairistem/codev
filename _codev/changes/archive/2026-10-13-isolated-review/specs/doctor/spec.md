## MODIFIED Requirements

### Requirement: `codev doctor` runs a fixed list of read-only checks

`codev doctor` SHALL evaluate the following checks, reported in this order, each
with a stable `id`, and report each one as `ok`, `missing` or `warning`,
with a stable `code` (`ok` when the check passes), a one-line message and,
when not `ok`, a one-line fix naming the exact command or skill:

| id | passes when | otherwise | code | fix |
|---|---|---|---|---|
| `config.rules` | `rules:` has at least one entry, inherited ones included | missing | `rules_missing` | `/codev-configure` |
| `config.language` | `language:` is set in `_codev/config.yaml` | missing | `language_missing` | add `language: <code>` to `_codev/config.yaml` |
| `config.keys` | `_codev/config.yaml` holds no key the running codev ignores (top level, `mcp` or `review`) | warning | `unknown_config_key` | `codev self-update` when the running codev does not satisfy `codev_version`, otherwise correct or remove the key, naming the keys |
| `config.roles` | every role setting is valid; informational, its message lists the active roles and the disabled ones | warning | `roles_invalid` | `codev validate` |
| `skills` | every configured workflow has its skill, generated by the running codev version, and the `propose` and `apply` skills are rendered for the project's review mode | missing | `skills_missing`, `skills_outdated` or `skills_review_mode` | `codev update` (`codev update --force` for a skill it preserves as edited by hand) |
| `sources` | every inherited git source is pinned in `_codev/codev.lock` and present in the cache, and the lock pins no undeclared source | missing (unpinned or not cached) or warning (undeclared pin) | `source_unpinned` or `lock_stale` | `codev sources update` |
| `codev_version` | the running codev satisfies the project's `codev_version`, when set, and the cached update check knows no newer release | missing (requirement not satisfied) or warning (newer release known) | `codev_version_unsatisfied` or `update_available` | `codev self-update`, or `codev self-update --version <X.Y.Z>` when the running codev is above the requirement |
| `specs` | at least one main spec exists | missing | `no_main_spec` | `/codev-propose`, noting that documenting existing behavior is planned work |
| `decisions` | at least one decision is `accepted`, local or inherited | warning | `no_accepted_decision` | `codev decision new "<title>"` |
| `validate` | `codev validate` reports no error and no warning | missing (errors) or warning (warnings only) | `validate_errors` or `validate_warnings` | `codev validate` |
| `claude_md` | `CLAUDE.md` holds the codev managed section | missing | `claude_md_section_missing` | `codev init` |
| `ci` | a file of `.github/workflows/` or `.gitlab-ci.yml` runs `codev validate` | missing | `ci_validate_missing` | `codev init` on GitHub, otherwise add `codev validate --strict` to the pipeline |
| `pr_template` | the pull request template holds the codev managed section — GitHub repositories only | missing | `pr_template_section_missing` | `codev init` |
| `changelog` | `CHANGELOG.md` exists and its managed `[Unreleased]` section matches what `codev changelog` would generate now | warning | `changelog_missing` (no file) or `changelog_outdated` | `codev changelog --write` |

The `pr_template` check MUST be absent from the report when the repository
is not a GitHub repository. A project without any inherited source passes
`sources`. A CI line is recognized when it names `codev` and then
`validate`, so `cargo run --bin codev -- validate` counts.

When the running codev does not satisfy `codev_version` because it is
above the requirement's upper bound, the fix MUST be
`codev self-update --version <X.Y.Z>`, a plain `codev self-update` refusing
to downgrade. `X.Y.Z` is, in this order of preference: the latest release
known to the update cache, when it satisfies the requirement; the highest
version the requirement admits, when an upper bound names it exactly (`<=`
or `=` with a full version); the lowest version the requirement admits,
when it has a lower bound. When none applies, the fix names the
requirement and asks for a release that satisfies it. When the running
codev is below the requirement, the fix stays `codev self-update`.

The `codev_version` check reads the per-user update cache that
`codev status` maintains and never refreshes it: with no cache, or with
`CI` set or `CODEV_NO_UPDATE_CHECK=1`, it only evaluates the requirement.

`codev doctor` MUST NOT write any file or access the network. The only
process it MAY spawn is `git`, for the local, read-only queries the
`changelog` check needs; outside a git repository, that check compares
with every archived change. Outside a codev project, it fails with the code
`no_codev_root`.

#### Scenario: A freshly initialized project

- **GIVEN** a project just initialized with `codev init --yes` outside
  GitHub, without rules, specs or decisions, and no newer codev release
  known
- **WHEN** the user runs `codev doctor`
- **THEN** `config.rules` and `specs` are `missing`, `decisions` is a
  `warning`, `ci` is `missing`
- **AND** `config.keys`, `config.roles`, `config.language`, `skills`, `sources`,
  `codev_version`, `claude_md` and `validate` are `ok`
- **AND** `changelog` is a `warning` with the code `changelog_missing`
- **AND** no `pr_template` check is reported

#### Scenario: Outdated skills

- **GIVEN** a project whose skills were generated by an earlier codev
  version
- **WHEN** the user runs `codev doctor`
- **THEN** `skills` is `missing` with the code `skills_outdated` and the fix
  `codev update`

#### Scenario: An unpinned git source

- **GIVEN** a project declaring a git source absent from
  `_codev/codev.lock`
- **WHEN** the user runs `codev doctor`
- **THEN** `sources` is `missing` with the code `source_unpinned` and the
  fix `codev sources update`

#### Scenario: CI recognized through `cargo run`

- **GIVEN** a GitHub project whose `.github/workflows/ci.yml` runs
  `cargo run --bin codev -- validate --strict`
- **WHEN** the user runs `codev doctor`
- **THEN** `ci` is `ok`

#### Scenario: Doctor writes nothing

- **GIVEN** any codev project
- **WHEN** the user runs `codev doctor`
- **THEN** no file of the project is created or modified

#### Scenario: Outside a codev project

- **GIVEN** a folder with no `_codev/` above it
- **WHEN** the user runs `codev doctor`
- **THEN** the command fails with the code `no_codev_root`

#### Scenario: CHANGELOG.md up to date

- **GIVEN** a project where `codev changelog --write` was just run
- **WHEN** the user runs `codev doctor`
- **THEN** `changelog` is `ok`

#### Scenario: CHANGELOG.md behind the archive

- **GIVEN** a project whose `CHANGELOG.md` managed section predates the
  latest archived change
- **WHEN** the user runs `codev doctor`
- **THEN** `changelog` is a `warning` with the code `changelog_outdated`
  and the fix `codev changelog --write`
- **AND** the exit code of `codev doctor --strict` is unaffected by it

#### Scenario: Running codev below the project's requirement

- **GIVEN** a project with `codev_version: ">=0.7"` and codev 0.6.0 running
- **WHEN** the user runs `codev doctor`
- **THEN** `codev_version` is `missing` with the code
  `codev_version_unsatisfied` and the fix `codev self-update`

#### Scenario: A newer release is known

- **GIVEN** a project without `codev_version`, and an update cache knowing
  a release newer than the running codev
- **WHEN** the user runs `codev doctor`
- **THEN** `codev_version` is a `warning` with the code `update_available`
  and the fix `codev self-update`
- **AND** no network request is made

#### Scenario: Running codev above the project's requirement

- **GIVEN** a project with `codev_version: ">=0.5, <0.7"`, codev 0.7.1
  running, and an update cache whose latest known release is 0.6.4
- **WHEN** the user runs `codev doctor`
- **THEN** `codev_version` is `missing` with the code
  `codev_version_unsatisfied` and the fix
  `codev self-update --version 0.6.4`

#### Scenario: Running codev above an exact upper bound, no usable cache

- **GIVEN** a project with `codev_version: "<=0.6.2"`, codev 0.7.0 running,
  and no update cache
- **WHEN** the user runs `codev doctor`
- **THEN** `codev_version` is `missing` with the fix
  `codev self-update --version 0.6.2`

#### Scenario: Running codev above a requirement with no exact bound

- **GIVEN** a project with `codev_version: "^0.5"`, codev 0.6.0 running, and
  an update cache whose latest known release, 0.6.0, does not satisfy it
- **WHEN** the user runs `codev doctor`
- **THEN** `codev_version` is `missing` with the fix
  `codev self-update --version 0.5.0`

#### Scenario: An unknown configuration key

- **GIVEN** a project whose `_codev/config.yaml` holds the top-level key
  `review_policy`, unknown to the running codev, which satisfies
  `codev_version`
- **WHEN** the user runs `codev doctor`
- **THEN** `config.keys` is a `warning` with the code `unknown_config_key`
  whose message names `review_policy`
- **AND** its fix tells to correct or remove the key
- **AND** the exit code of `codev doctor --strict` is unaffected by it

#### Scenario: An unknown key with an unsatisfied requirement

- **GIVEN** a project whose `_codev/config.yaml` holds an unknown key and
  `codev_version: ">=9"`
- **WHEN** the user runs `codev doctor`
- **THEN** `config.keys` is a `warning` with the fix `codev self-update`

#### Scenario: The roles in effect

- **GIVEN** a project whose configuration holds `roles: { newcomer: never }`
- **WHEN** the user runs `codev doctor`
- **THEN** `config.roles` is `ok` and its message lists the active roles
  and names `newcomer` as disabled

#### Scenario: An invalid role setting

- **GIVEN** a project whose configuration holds `roles: { reviewer: never }`
- **WHEN** the user runs `codev doctor`
- **THEN** `config.roles` is a `warning` with the code `roles_invalid`
  and the fix `codev validate`
- **AND** `validate` is `missing`

## ADDED Requirements

### Requirement: The `skills` check compares the skills with the review mode

When every configured skill is present and generated by the running
codev, the `skills` check of `codev doctor` SHALL be `missing` with the
code `skills_review_mode` if the `propose` or `apply` skill was rendered
for another review mode than the project's: it lists the sub-agent tool
while the mode is `inline`, or does not while it is `isolated`. The
message SHALL name the skills and the project's mode, and the fix SHALL
be `codev update`, adding `codev update --force` for a skill that
`codev update` preserves as edited by hand. A missing or outdated skill
keeps its own code, which takes precedence.

#### Scenario: Skills rendered before switching to isolated

- **GIVEN** a project whose skills were generated in inline mode by the
  running codev, then `review: { mode: isolated }` in its configuration
- **WHEN** the user runs `codev doctor --json`
- **THEN** the `skills` check is `missing` with the code
  `skills_review_mode`, naming `codev-propose`, `codev-apply` and
  `isolated`, and the fix `codev update`

#### Scenario: A skill of the other mode edited by hand

- **GIVEN** a project in isolated mode whose `codev-apply` skill was
  generated in inline mode by the running codev, then edited by hand
- **WHEN** the user runs `codev doctor --json`
- **THEN** the `skills` check's code is `skills_review_mode` and its fix
  names `codev update --force`

#### Scenario: Skills in step with the mode

- **GIVEN** a project in isolated mode where `codev update` just ran
- **WHEN** the user runs `codev doctor --json`
- **THEN** the `skills` check is `ok`

#### Scenario: An outdated skill takes precedence

- **GIVEN** a project in isolated mode whose `codev-propose` skill was
  generated by an earlier codev in inline mode
- **WHEN** the user runs `codev doctor --json`
- **THEN** the `skills` check's code is `skills_outdated`
