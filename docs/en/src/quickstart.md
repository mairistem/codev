# Quickstart

This chapter takes you from an empty repository to your first archived change
in about five minutes. It assumes Compagnon is [installed](installation.md) and
that you use Claude Code.

Each step shows the Claude Code way first (recommended), then the plain CLI
equivalent, so you can see what the skills do underneath. The command output
below is real, with the project path shortened to `/home/you/acme-app`.

## 1. Initialize the project

At the root of your repository:

```bash
compagnon init
```

On a terminal, `compagnon init` asks at most two questions — which workflows to
install and a free-text context for the skills — then writes the files. Pass
`--yes` to accept every default without prompting, as in this run:

```bash
compagnon init --yes --language en
```

```text
compagnon initialized in /home/you/acme-app

  Structure   _compagnon/ — specs, decisions, changes, schemas
  Skills      compagnon-propose, compagnon-explore, compagnon-onboard, compagnon-apply, compagnon-sync, compagnon-archive, compagnon-update, compagnon-configure → .claude/skills/

  Repository integration
    + CLAUDE.md                          created
    + .github/workflows/compagnon.yml        created
    + .github/PULL_REQUEST_TEMPLATE.md   created

  17 file(s) created, 0 updated

→ Recommended next step: in Claude Code, run /compagnon-configure.
  Claude will analyze the project and enrich _compagnon/config.yaml
  (context, per-artifact rules) — ~30 seconds.

Or skip this step and run /compagnon-propose <an-idea> directly.

Run `compagnon doctor` to see the 2 setup check(s) still to fix.
```

This repository has a GitHub remote, so Compagnon also wrote a CI workflow and a
pull request template; see step 5 below.

Restart Claude Code (or start a new session) so it discovers the new skills.

### What `compagnon init` does

1. **Probes the environment**, silently: project manifests (`Cargo.toml`,
   `package.json`, `pyproject.toml`, `go.mod`, `pom.xml`), the license file,
   the presence of `.github/workflows/`, your locale, and the MCP servers
   declared in `.mcp.json`, `.claude/settings.json` and `~/.claude.json`.
   `--no-detect` skips the probe.
2. **Asks at most two questions** when run on a terminal: which workflows to
   install (full, minimal, or custom) and a free-text context for the skills.
   An empty answer to the context question opens `$EDITOR` on a skeleton. A
   detected Jira MCP server is confirmed rather than asked for. With `--yes`,
   or when stdin is not a terminal (CI, pipes), no question is asked.
3. **Creates the `_compagnon/` tree** — `specs/`, `decisions/`, `changes/`,
   `changes/archive/`, `schemas/` — and a `_compagnon/config.yaml` in which every
   detected value carries a comment saying where it came from:

   ```yaml
   # compagnon configuration — generated by `compagnon init`.
   # Hand-editable: each non-trivial field carries its source as a comment.

   schema: spec-driven

   # Language skills write the artifacts in (proposal, design, tasks,
   # specs). Structural keywords such as `## Why` or `### Requirement:`
   # follow it when compagnon ships the language, and stay in English otherwise.
   # set with `compagnon init --language`
   language: en

   workflows:
     - propose
     - explore
     - onboard
     - apply
     - sync
     - archive
     - update
     - configure
   ```

4. **Installs the skills** into `.claude/skills/compagnon-<workflow>/SKILL.md`.
5. **Integrates Compagnon into the repository**, unless you opt out:
   - a Compagnon section in `CLAUDE.md`, created if missing, telling Claude Code
     that the specs are authoritative and that behavior changes go through
     `/compagnon-propose` then `/compagnon-apply`;
   - on GitHub, `.github/workflows/compagnon.yml`, which runs
     `compagnon validate --strict` on every push and pull request;
   - on GitHub, a Compagnon section in the pull request template.

   Compagnon's text sits between `<!-- compagnon:begin -->` and `<!-- compagnon:end -->`
   markers and never replaces yours. `--no-claude-md`, `--no-ci`,
   `--no-pr-template` and `--no-integration` skip these files. See
   [Repository integration and compagnon doctor](guides/repository-integration.md).
6. **Declares inherited sources** given with `--inherit`, and pins the git
   ones right away. See [Inherited sources](guides/inherited-sources.md).

If `_compagnon/config.yaml` already exists, `compagnon init` leaves it untouched: it
only installs or refreshes the skills and the repository integration.

`compagnon doctor` then lists what the setup still lacks — here, rules and a first
spec — with the command or skill that fixes each item:

```bash
compagnon doctor
```

> **Note**
> The recommended next step, `/compagnon-configure`, lets Claude read your
> README, contributing guide and a sample of your code, then propose a richer
> `context:` and per-artifact `rules:` for the configuration. It shows a diff
> and writes nothing without your confirmation.

## 2. Propose a change

In Claude Code, describe what you want:

```text
/compagnon-propose add a dark mode that follows the system preference
```

The skill picks a kebab-case name (here `add-dark-mode`), creates the change,
then writes its four planning artifacts in dependency order: `proposal.md`,
the spec deltas under `specs/`, `design.md` and `tasks.md`. It modifies no
code, and stops once the plan is ready for your review.

Underneath, it starts with:

```bash
compagnon new change add-dark-mode --goal "Let users switch the UI to a dark theme"
```

```text
Change `add-dark-mode` created
  Location  /home/you/acme-app/_compagnon/changes/add-dark-mode
  Schema    spec-driven

Next step: `compagnon instructions --change add-dark-mode` shows the artifact to write.
```

`compagnon status` shows which artifacts exist and which are waiting on others:

```text
Change: add-dark-mode
Schema: spec-driven

  [ ] proposal
  [-] specs (waiting on: proposal)
  [-] design (waiting on: proposal)
  [-] tasks (waiting on: specs, design)

Planning: 0/4 artifacts
Next:     proposal
```

For each artifact, the skill asks Compagnon for everything it needs to write it —
the schema's instruction, the template, the project context and rules, the
language, and the files it depends on:

```bash
compagnon instructions proposal --change add-dark-mode
```

```text
Artifact: proposal (change `add-dark-mode`, schema spec-driven)
Write to: /home/you/acme-app/_compagnon/changes/add-dark-mode/proposal.md
Language: en — prose and structural keywords in en

Instruction:

Write the document that establishes WHY this change is needed.
…
```

Skills call the same command with `--json` and receive a
[stable document](reference/json-output.md) instead.

## 3. Review the plan

Once the skill is done, read the artifacts in
`_compagnon/changes/add-dark-mode/`. The spec delta is the heart of the plan — it
states the behavior the change adds, as testable requirements:

```markdown
## Purpose

Let users choose the color theme of the interface.

## ADDED Requirements

### Requirement: Theme follows the system preference by default

The application SHALL render with the operating system's color scheme until the user picks a theme.

#### Scenario: No theme chosen yet

- **GIVEN** a user who has never changed the theme setting
- **WHEN** their operating system is set to dark mode
- **THEN** the application renders with the dark theme
```

Ask Claude for adjustments with `/compagnon-update`, or edit the files yourself.
Then check that planning is complete and the change is valid:

```bash
compagnon status
```

```text
Change: add-dark-mode
Schema: spec-driven

  [x] proposal
  [x] specs
  [x] design
  [x] tasks

Planning: 4/4 artifacts
Planning is complete.
```

```bash
compagnon validate add-dark-mode
```

```text
change add-dark-mode — _compagnon/changes/add-dark-mode
  ✓ no issues

1 item(s) validated, no issues.
```

> **Note**
> A change with no spec delta fails validation with
> `zero_delta_without_marker`. That is deliberate: it keeps specs from being
> forgotten. A change that really has no behavioral impact — a refactor,
> tooling, documentation — declares `skip_specs: true` in its `change.yaml`.

## 4. Implement

```text
/compagnon-apply add-dark-mode
```

The skill reads `tasks.md`, works through each unchecked task in order, runs
the verification each task names, and checks the box. It stops at the first
blocker or ambiguity and asks you. It is the only Compagnon skill that modifies
code outside `_compagnon/`.

## 5. Archive

When the tasks are done:

```text
/compagnon-archive add-dark-mode
```

Or with the CLI:

```bash
compagnon archive --change add-dark-mode
```

```text
Archived change `add-dark-mode`

Created:
  /home/you/acme-app/_compagnon/specs/ui/theme/spec.md

Moved to: /home/you/acme-app/_compagnon/changes/archive/2026-09-30-add-dark-mode
```

Archiving validates the change, merges its deltas into the main specs — here
it creates `_compagnon/specs/ui/theme/spec.md`, since `ui/theme` is a new
capability — and moves the change folder to the dated archive. Commit the
result: the main specs now describe the behavior you just shipped.

## What's next

- Every later change follows the same cycle, from a one-line fix to a
  capability rewrite. [The workflow](workflow.md) describes each step in
  detail.
- [Concepts](concepts.md) explains deltas, capabilities and decisions.
- `/compagnon-onboard` gives a read-only tour of Compagnon and of your project's
  current state, with a recommended next action.
